# Development Rules

## 总原则

开发目标是交付一个真实可安装、可运行的软件，而不是只生成界面截图或概念代码。

每次开发必须优先保证：

1. 程序可以启动

2. 核心流程可以运行

3. 测试可以执行

4. 错误可以被理解

5. 修改不会破坏已有功能

## 禁止事项

开发过程中禁止：

- 未经说明修改产品范围

- 一次性重写整个项目

- 删除已有测试来让测试通过

- 使用假数据冒充真实功能

- 在生产代码中写死 API Key

- 将所有代码写进一个文件

- 在 UI 主线程执行长时间任务

- 忽略异常

- 使用空的 `except`

- 使用未经授权的图片爬虫

- 只交付源代码而不提供打包方式

- 声称功能完成但没有运行测试

## 开发方式

每个任务按照以下顺序进行：

1. 阅读现有文档

2. 阅读现有代码

3. 明确本次任务范围

4. 编写或更新测试

5. 实现功能

6. 运行测试

7. 运行应用

8. 记录修改内容

9. 更新任务状态

## 小步修改

每次只完成一个明确目标。

好的任务：

```Plain Text
实现项目创建和 project.json 保存。
```

不好的任务：

```Plain Text
完成整个视频生成软件。
```

每次修改尽量控制在可审查范围内。

## 代码要求

- 函数保持单一职责

- 对公共函数添加类型标注

- 重要模块添加 docstring

- 文件和变量使用清晰名称

- 不使用无意义缩写

- UI、业务逻辑和外部接口分离

- 外部服务通过 Provider Interface 调用

- FFmpeg 命令通过独立模块封装

- 文件路径使用跨平台路径处理方式

## 测试要求

每个核心模块至少包含单元测试。

必须测试：

- 文案拆分

- 项目保存和读取

- 关键词结果格式

- 图片结果格式

- 文件下载失败

- TTS 失败

- 字幕时间生成

- FFmpeg 命令生成

- 非法路径

- 取消生成任务

外部 API 测试应使用 mock。

集成测试可以使用极短的本地样例素材。

## 日志要求

日志必须记录：

- 应用启动

- 项目打开

- 项目保存

- 图片搜索开始和结束

- 图片下载结果

- TTS 任务状态

- FFmpeg 执行状态

- 错误堆栈

- 最终输出位置

日志不得记录：

- 完整 API Key

- 用户密码

- 不必要的用户隐私数据

## 配置要求

所有可变配置必须集中管理。

例如：

- 输出目录

- 缓存目录

- 超时时间

- 重试次数

- 图片服务

- TTS 服务

- FFmpeg 路径

禁止在多个业务文件中重复写死配置。

## 文档同步

代码行为发生改变时，需要检查：

- README 是否需要更新

- PRODUCT\_SPEC 是否需要更新

- ARCHITECTURE 是否需要更新

- ACCEPTANCE\_TESTS 是否需要更新

- TASK 是否需要更新

未经明确批准，不得直接修改产品需求来适配代码缺陷。

优先修复代码，而不是降低需求。

## 完成声明格式

每次任务结束时，开发 AI 必须报告：

```Plain Text
Completed:
- 完成了什么

Files changed:
- 修改了哪些文件

Tests:
- 执行了哪些测试
- 测试结果

Manual verification:
- 手动验证了什么

Known limitations:
- 仍然存在什么限制

Next recommended task:
- 下一步建议
```

不得只回复“完成了”。
